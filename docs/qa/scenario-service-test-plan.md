## Testability findings sent to pm

The ACs are testable as written. Points found while planning and verifying, for pm (none blocks sign-off):

1. **Tags with Unicode whitespace.** The Gherkin parser splits tag lines on `@` and only rejects ASCII whitespace inside
   a tag, so `@a<U+00A0>b` is a stored tag. D19 #5 assumes "a Gherkin tag can never contain whitespace": such a tag is
   listed by the catalogue but the filter must refuse it (AC-5.7 row 3). Accept, or change the rule.
2. **Unicode normalization and full case folding in paths.** `features/é.feature` (NFC) and `features/e<U+0301>.feature`
   (NFD), or `ß` and `SS`, are different paths for ICU `lower()`, so both are stored. On macOS (
   normalization-insensitive)
   or with full case folding they are one file. D10's goal "an export never collides on case-insensitive file systems"
   isn't fully met. Accept, or normalize.
3. **`# encoding:` pragma.** The parser honours it: a valid charset re-decodes the UTF-8 text, so the stored text says
   `Café` while the derived name is `CafÃ©` (consistent with Cucumber reading the same bytes). An unknown charset is
   BUG-scenario-service-1. Decide whether pragmas other than UTF-8 should be rejected.
4. **Size of a feature.** 1,000,000 code points allow about 37,000 scenarios; a save then takes about a minute (see
   BUG-scenario-service-2). The spec has no element-count limit and the NFR only covers 1,000-line saves.
5. **Contract wording "forwarded unchanged".** scenario-service sends `Authorization: Bearer <token>` rebuilt from the
   token, so a `bearer` scheme arrives at auth-service as `Bearer`. Harmless; the wording could say "the caller's
   token".
6. **Framework DEBUG logs.** With `org.springframework.security` at DEBUG, Spring Security logs request URLs with their
   query string (a tag value). D17 covers the application's loggers only; a README note would help operators.

## Risks and items not covered

- Performance is measured, not asserted (NFR is informational); the 1 s / 200 ms targets are reported in the QA report.
- The JDK HTTP client's own retry behaviour (BUG-scenario-service-4) depends on the JDK version.
- Container-level and firewall rejections (Tomcat, Spring Security) are verified over real HTTP only in the manual run.
- No frontend exists; browser CORS for `If-Match` is irrelevant because `baseVersion` is a body field (D9).
- auth-service's real C5 timing under load isn't measured; the stub and an unreachable address stand in for it.
