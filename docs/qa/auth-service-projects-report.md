## Bugs

### BUG-auth-service-projects-1: non-canonical UUID strings are accepted as ids, so one project has many valid ids

- Severity: S4 Minor
- Affected: auth-service, every UUID path variable. Shown on `GET /internal/projects/{projectId}/access` and
  `GET /api/orgs/{orgId}/projects/{projectId}`.
- Linked AC: contract
  `docs/api/auth-service.openapi.yaml#/paths/~1internal~1projects~1{projectId}~1access/get/parameters/0` (
  `format: uuid`, "A value that isn't a UUID is 400 `MALFORMED_REQUEST`"); the spirit of AC-7.2 and AC-2.3 row 5. The AC
  rows themselves (`not-a-uuid`) pass.
- Commit tested: `6fd4434` (+ user edits). **Pre-existing:** phase-1 paths behave the same way.
- Steps to reproduce:
    1. `GET http://localhost:8081/internal/projects/1-1-1-1-1/access` with any valid `Authorization: Bearer <token>`.
    2. With Checkout's id `cc9e7d0d-e766-45a4-a667-066a1792ecf7` and a token that has access,
       `GET http://localhost:8081/internal/projects/cc9e7d0d-e766-45a4-a667-66a1792ecf7/access` (leading zero of the
       last group removed).
    3. Also `3b9d5c1e-0000-4000-8000-0000000000f` (35 characters) and `ab3b9d5c1e-0-0-0-0` (over-long group, silently
       masked to `3b9d5c1e-…`).
- Expected: 400 `MALFORMED_REQUEST` for every string that isn't a canonical 8-4-4-4-12 UUID.
- Actual: step 1 gives 403 `FORBIDDEN`; step 2 gives **200** with `"projectId":"cc9e7d0d-e766-45a4-a667-066a1792ecf7"`,
  which differs from the id in the request.
- Evidence: Spring converts path variables with `UUID.fromString`, which is lenient on Java 17. A scratch probe gave
  `1-1-1-1-1` → `00000001-0001-0001-0001-000000000001` and `ab3b9d5c1e-0-0-0-0` →
  `3b9d5c1e-0000-0000-0000-000000000000`. Authorization still uses the parsed UUID, so **nothing is exposed**. The risk:
  a consumer that keys caches or audit records on the path string can see two strings for one project.
- Suggested owner: backend-swe (a strict UUID check for path variables), scheduled by pm. It isn't a phase-2 regression.

### BUG-auth-service-projects-2: a number or boolean is accepted as a project name

- Severity: S4 Minor
- Affected: auth-service, `POST /api/orgs/{orgId}/projects` and `PATCH .../projects/{projectId}`. The same applies to
  every string field (Jackson scalar coercion).
- Linked AC: contract `docs/api/auth-service.openapi.yaml#/components/schemas/CreateProjectRequest/properties/name` (
  `type: string`); unspecified by the ACs.
- Commit tested: `6fd4434` (+ user edits). **Pre-existing** behaviour of every string field since phase 1.
- Steps to reproduce:
    1. `POST /api/orgs/{acme}/projects` as an organization admin, `Content-Type: application/json`, body `{"name":123}`.
- Expected: 400 `MALFORMED_REQUEST` (a JSON number isn't a string), as for `{"name":["a"]}`.
- Actual: 201 with `"name":"123"`; `{"name":true}` gives 201 `"true"`.
- Evidence: scratch probe on 2026-10-13, under `qa/`, deleted afterwards. Roles were already protected against numbers
  by `fail-on-numbers-for-enums` (phase-1 E24), but strings aren't.
- Suggested owner: pm decides whether this is worth a follow-up. If so, backend-swe disables scalar coercion for textual
  fields (`spring.jackson` coercion config).
