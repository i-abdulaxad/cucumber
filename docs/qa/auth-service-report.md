### Assessment: Hibernate's WARN lines with SQL

- **Lock timeouts (the case backend-swe reported):** Hibernate's `org.hibernate.orm.jdbc.error` logs 2 WARN lines:
  `HHH000247: ErrorCode: 50200, SQLState: HYT00`, and `Timeout trying to lock table "ORGANIZATIONS"; SQL statement:`
  followed by the SQL. The SQL is the **prepared statement with `?` placeholders only**, for example
  `select o1_0.id,… from organizations o1_0 where o1_0.id=? for update [50200-240]`, and
  `… from invitations i1_0 where i1_0.token=? for update`. **No bound values** appear: no id, token, email or password.
  `QaFixRoundTest`'s 4 real-lock tests assert this for each request's log, including that the acceptance token never
  appears. There's no ERROR and no stack trace, so it meets AC-1.9 and the NFR "never log … tokens". **Not a bug.**
- **Unique-constraint violations (the AC-2.11 path), found while checking this:** the same logger writes H2's error
  message, and **that message does contain the conflicting value**:
  `Unique index or primary key violation: "PUBLIC.CONSTRAINT_INDEX_4 ON PUBLIC.USERS(EMAIL NULLS FIRST) VALUES ( /* 796 */ 'zed@example.com' )"; SQL statement: insert into users (…) values (?,?,?,?,?,?,?,?)`.
  The password hash and the other bound values aren't in it. Only the email is, because it's the key value. Filed as
  BUG-5 (S4). PostgreSQL's message has the same kind of detail (`Key (email)=(…) already exists`).

### BUG-auth-service-4: A 72-byte password also matches with any suffix at login (closed in the fix round)

- Severity: S4 Minor
- Affected: auth-service, `POST /api/auth/login`
- Linked AC: AC-2.4 ("wrong credentials give the same 401"). Outside its example rows; related to A6 and E17.
- Commit tested: `32eee07` + working tree
- Steps to reproduce:
    1. `POST /api/auth/register` `{"email":"a72@example.com","password":"AAAA…A" (72 × A),"fullName":"E"}` returns 201.
    2. `POST /api/auth/login` `{"email":"a72@example.com","password":"AAAA…AZ" (72 × A + "Z")}`.
- Expected: 401 `INVALID_CREDENTIALS`.
- Actual: **200 with an access token**. The same happens with 24 × `€` + `X`. Passwords shorter than 72 bytes aren't
  affected: 71 × A + `Z` returns 401, and `Secret123!X` returns 401 (

- Evidence: scratch exploration (R8). Root cause: BCrypt only uses the first 72 bytes when checking, and
  `LoginRequest.password` has no byte limit. The risk is negligible: the caller must already know the full 72-byte
  password.
- Suggested owner: backend-swe (answer `INVALID_CREDENTIALS` for login passwords over 72 bytes, without a validation
  error, to keep AC-2.4's uniform answer)

## Other observations (not bugs)

- **jjwt 0.12.5:** every AC-3.1 row and 25 more forged-token variants are rejected quietly, with no ERROR log. A valid
  HS512 token with the shared secret and `"zip":"DEF"` (a compressed payload) is accepted. Only a holder of the secret
  can make one, so there's no risk, but the gateway's behaviour for such tokens wasn't compared.
- **Problem `instance` holds the acceptance token** on every accept error, because `instance` is the path (D2). It is
  echoed only to the caller who sent it, and it's never logged by auth-service (`QaInvitationSecurityTest`,
  `QaLeakageTest`). Question Q3.
- **Dev profile only:** devtools turns on `spring.mvc.log-resolved-exception`, so the dev log has WARN lines such as
  `Resolved [EmailAlreadyExistsException: Email already exists: ana@example.com]`. These contain no secrets. Without
  devtools (tests, packaged jar), they don't appear.
- **Token enumeration:** an unknown token and a near-miss of a real token get byte-identical 404 bodies. The average
  time for an unknown token versus a revoked token was 0.5–1.7 ms versus 1.0–2.1 ms (noisy, no BCrypt in either). With
  192-bit tokens, that's not a practical oracle.
- **ERD:** the generated schema matches the `auth_service` group exactly. That's 46 columns with type, length and
  nullability, 5 enums with their values, 4 unique constraints and 12 foreign keys (`QaSchemaTest`, plus the dev DDL in
  the log, for example `invitations.token varchar(255) unique`, `status enum (…)`).
- **Unicode:** NFC and NFD spellings of an email are two accounts, `İNCI@` becomes `i̇nci@`, the Kelvin sign becomes
  ASCII `k`, and organization names made only of Unicode spaces, or containing U+0000, are accepted. All of this is
  unspecified (Q4, Q5).

## Gaps and risks

- Everything runs on H2. Lock timeouts, unique-constraint messages, enum DDL and U+0000 behave differently on
  PostgreSQL (phase 4).
- The concurrency results are probabilistic: repeated, and run 3 × with no failure, but not a proof. The locking order
  was also reviewed in code: invite locks the organization; accept locks the invitation and then the organization;
  revoke locks the invitation; change and remove lock the organization. No lock-order inversion was found.
- The lock-timeout 500 (deviation 1) is reproduced manually only, until the approved follow-up maps it.
- US-3 is verified directly on 8081, because through the gateway the gateway answers 401 first (Known issue 1).
- Not tested: rate limiting and brute force (out of scope), and phase 2–4 features.
